# EduTrace API contract (proposed)

> **Status: proposal, not a working backend.** The routes below are the paths
> `HttpApiClient` calls. They are intentionally conventional Django REST
> Framework paths and will be finalised with the backend team. Nothing in this
> repository serves or proves these endpoints. The OpenAPI schema generated by
> DRF is the source of truth once the backend exists.

Client implementation: `src/lib/api/httpApiClient.ts`
Shared HTTP client: `src/lib/api/httpClient.ts`
Type contracts: `src/lib/api/services.ts`, `src/lib/api/types.ts`

---

## 1. Conventions

- Base URL: `VITE_API_BASE_URL`, for example `https://api.example.gov.in/api/v1`
- JSON request/response, UTF-8, `Accept: application/json`
- Authentication: `Authorization: Bearer <access token>` from Keycloak (OIDC,
  Authorization Code + PKCE). The frontend keeps tokens in memory only.
- All mutations are authorized and scoped by Django. The frontend guards are
  usability only.
- Timestamps are ISO 8601 UTC (`2026-10-25T09:15:00Z`).
- Identifiers are opaque strings in the UI; the backend may use UUIDs.
- Pagination query: `page`, `page_size`, `search`, `ordering`
- Filters used by the UI: `academic_year`, `state`, `institution`,
  `course`, `status`, `apaar_status`, `enrolment_status`,
  `validation_status`, `submission_status`, `severity`, `read`,
  `date_from`, `date_to`
- Paginated response:

```json
{
  "count": 385,
  "next": "https://api.example.gov.in/api/v1/students/?page=2",
  "previous": null,
  "page": 1,
  "page_size": 25,
  "results": []
}
```

- Error response:

```json
{
  "detail": "Human-readable message.",
  "code": "VALIDATION_ERROR",
  "errors": { "reg_number": ["This field is required."] },
  "request_id": "8f2c..."
}
```

The HTTP client normalises these into `ApiError` with `status`, `code`,
`message`, `details` and `requestId`. It also maps timeouts to `408/TIMEOUT` and
transport failures to `NETWORK`.

## 2. Endpoints

### Institutions

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/institutions/` | Registry, filters, search |
| GET | `/institutions/{id}/` | Institution detail |
| PATCH | `/institutions/{id}/` | Institution profile update (authorized fields only) |
| POST | `/institutions/{id}/verification/` | Verify / request correction / reject, with reason |

Verification payload:

```json
{ "decision": "Verified", "reason": "Approval reference confirmed against the 2026-27 extract." }
```

`decision` ∈ `Verified`, `Correction Required`, `Rejected`, `Under Verification`.

The backend must reject institution-user edits to authoritative approved intake.

### Courses and approved intake

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/courses/` | Course references with revisions |
| GET | `/courses/{id}/` | Course detail |
| POST | `/courses/{id}/intake-revisions/` | Append an authorized intake revision |

```json
{
  "approved_intake": 120,
  "approval_ref": "AICTE/APPROVAL/2026-27/WR-11284-C",
  "effective_date": "2026-06-01",
  "academic_year": "2026-27",
  "verification_status": "Verified",
  "reason": "Revised sanction letter received and checked."
}
```

Only AICTE administrative roles may call this endpoint. Revisions are append-only;
existing references are not overwritten.

### Students

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/students/` | Scoped registry with filters and pagination |
| GET | `/students/{id}/` | Detail with issues, submissions, audit |
| POST | `/students/` | Create a record |
| PATCH | `/students/{id}/` | Update with `change_reason` |

```json
{
  "name": "Synthetic Student",
  "enrolment_status": "Active",
  "apaar_id": "999123456789",
  "change_reason": "Corrected spelling against the admission register."
}
```

The backend derives institution scope from the authenticated principal. Clients
must not be able to read or write another institution's records by changing an ID.

### CSV uploads

| Method | Path | Purpose |
| --- | --- | --- |
| POST | `/uploads/validate/` | Multipart file + `institution` + `academic_year`; runs deterministic rules |
| POST | `/uploads/{batch_id}/commit/` | Convert the validated batch into a submission |
| GET | `/uploads/` | Batch history |

Validation response (row-level, nothing silently discarded):

```json
{
  "batch_id": "batch-...",
  "summary": {
    "total_rows": 4,
    "valid_records": 2,
    "invalid_records": 2,
    "duplicate_candidates": 0,
    "missing_fields": 2,
    "warnings": 1,
    "fatal_errors": 2
  },
  "rows": [
    {
      "row_number": 14,
      "values": { "registration_number": "", "...": "..." },
      "findings": [
        {
          "rule_id": "STU-001",
          "rule_name": "Mandatory field missing",
          "severity": "High",
          "field": "registration_number",
          "evidence": "Value is empty.",
          "suggested_action": "Enter the registration number issued by the institution."
        }
      ]
    }
  ]
}
```

Rules mirror `src/lib/validation/rules.ts`. Rule IDs and severities are part of
the contract so findings can be compared across frontend and backend.

Processing should be asynchronous for large files: the endpoint may return a
batch in `Validating` state and the client polls `GET /uploads/{batch_id}/`.
The demonstration client assumes a synchronous response.

### APAAR (simulated until an authorized adapter exists)

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/apaar/summary/` | Aggregate status counts |
| POST | `/apaar/verifications/` | Queue verification requests |

```json
{ "student_ids": ["stu-1", "stu-2"] }
```

The backend owns the adapter and credentials. No APAAR ID is generated by the
frontend. Until a live authorized source exists, responses must be marked
`Simulated` and must not be presented as verified.

### Validation issues

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/validation-issues/` | Scoped queue |
| GET | `/validation-issues/{id}/` | Detail and history |
| PATCH | `/validation-issues/{id}/` | Status, assignment, comment |

```json
{
  "status": "Correction Required",
  "assigned_to": "usr-3",
  "comment": "Admission date conflicts with the register."
}
```

Every transition is audit-logged with actor, timestamp and reason where relevant.

### Intake compliance and alerts

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/intake-compliance/` | Cohort comparison: approved, active, pending, withdrawn, excess |
| POST | `/intake-alerts/review/` | Record a reasoned alert decision |

```json
{
  "key": "inst-1:crs-1-aid:2026-27",
  "status": "Reference Verification Required",
  "reason": "The approval extract for this programme is not verified."
}
```

Compliance must count only verified active enrolment, must use the reference for
the same institution/course/year, and must suppress excess when the reference is
unverified. It must not reject or delete student records.

### Submissions

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/submissions/` | Institution-scoped or national list |
| GET | `/submissions/{id}/` | Detail, timeline, reviewer comments |
| POST | `/submissions/{id}/review/` | Accept / reject / request correction |
| POST | `/submissions/{id}/resubmit/` | Institution resubmission with note |

```json
{ "decision": "request_correction", "reason": "Two rows have an unknown course." }
```

Decisions require a reason and are append-only. Acceptance in this frontend is a
workflow demonstration, not official AICTE acceptance.

### Notifications

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/notifications/` | Scoped list |
| POST | `/notifications/mark-read/` | `{ "ids": ["..."] }` |
| POST | `/notifications/mark-all-read/` | Mark all in scope |

### Reports

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/reports/definitions/` | Available reports and formats |
| GET | `/reports/{report_id}/export/?format=csv` | Server-generated export |

Production exports must come from the backend so the CSV reflects
server-authoritative data and authorization scope.

### Audit

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/audit-events/` | Read-only, filterable by actor, action, date, institution |

There is no write endpoint: audit events are produced by the backend as a side
effect of authorized operations.

### Portal users (administrative)

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/users/` | List portal users in scope |
| POST | `/users/` | Invite a user |
| PATCH | `/users/{id}/` | Change account status |

Production role assignment must be performed through Keycloak and audited by
Django. The demo UI is explicitly simulated.

### Duplicate candidates

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/duplicate-candidates/` | Evidence, no unnecessary personal data |
| POST | `/duplicate-candidates/review/` | Reasoned decision |

```json
{
  "key": "dup:apaar:999123456789",
  "status": "Request Institution Clarification",
  "reason": "Same identifier reported by two institutions with different names."
}
```

### System integrations

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/system/integrations/` | Adapter status for APAAR, AICTE, auth, DB, storage |

Statuses: `Simulated`, `Not Configured`, `Connected`, `Unavailable`, `Error`.
The UI must never infer `Connected` from the presence of mock data.

## 3. Suggested Django shape (non-binding)

- Apps: `accounts`, `institutions`, `courses`, `students`, `uploads`,
  `validation`, `submissions`, `apaar`, `audit`, `reports`
- PostgreSQL with constraints for unique `(institution, reg_number)` and an
  index on `apaar_id`; APAAR IDs are not globally unique by assumption in the UI,
  because duplicates are a review signal
- Permission classes per role and institution scope; object-level checks on every
  detail view
- Deterministic validation implemented once in Python and mirrored by the
  frontend rule IDs; the backend result is authoritative
- Celery + Redis tasks: CSV parsing/validation, APAAR verification polling,
  notification fan-out, report generation
- Private S3/MinIO buckets for uploads and exports; presigned, time-limited URLs;
  no public objects
- Append-only audit model; no update/delete API
- OpenAPI schema generated with `drf-spectacular`; frontend types generated from
  it and checked in CI

---

## 4. Contract changes

Any change to a rule ID, severity, status enum, pagination shape or error envelope
must be agreed before implementation, because the UI displays these values
directly. The frontend types in `src/types/` and `src/lib/api/services.ts` are the
current reference and should be regenerated from OpenAPI once it exists.
